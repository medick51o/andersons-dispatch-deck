Q1 LEAK FIXED?
- **No.** Nothing was changed; a lesson was learned. The incident's core fact — cloud agents carry their own model/mode selection and never read `cli-config.json` — means no file on disk can guard that lane. A guard that the guarded system cannot see is decoration.
- **The specific guard:** a scripted launch wrapper. All cloud-agent launches must go through one local CLI script that (a) refuses `maxMode:true` stacked with `effort:xhigh` and `speed:fast` unless a human types an override phrase, (b) verifies the target repo's MCP wiring passes the 15-check arm test *before* launch (the arm test currently arms seats; it must gate launches), and (c) hard-caps concurrent cloud agents at a small number (ESTIMATE: 2). Launching through the raw web UI must be treated as a policy violation, not a convenience.
- **Where the spend guard must live:** vendor-side, not client-side. Cursor exposes account-level usage/spend views and (on some tiers) hard limits; the operator must set the tightest vendor-side limit available on the dashboard and enable spend alerts, because that is the only enforcement point the cloud lane actually traverses. (STALE-FLAG: exact limit features on Cursor plans change frequently — verify current dashboard capabilities.)
- **Other lanes that bypass local config the same way:** the Cursor web dashboard's agent launcher, the mobile app, IDE-native background agents (distinct from cloud agents but also server-executed), Bugbot on PRs, scheduled/automated runs, Slack/Linear-triggered agents, and any seat added to a team plan. Each is a server-side execution path with its own model selection. The shared trait: *anything that executes on the vendor's infrastructure is governed by the vendor's settings, not yours.*
- **Failure mode nobody has thought of yet:** the meter itself is vendor-reported. The operator reads `bonusSpend` to measure the subsidy, but that field's own note says it may vary. The vendor can halve the subsidy silently, and the operator's "needle" would calmly report the new, worse reality as if nothing happened — because the needle is drawn by the party being measured against. There is no independent meter anywhere in the rig.

Q2 EFFICIENCY
- **Keep:** the persistent-session MCP pattern (stateful seats genuinely beat amnesiac one-shots), prompt-spill-to-file, and the allowance check — these solve real problems cheaply.
- **Cut:** the 400-lines-per-seat symmetry. A competent engineer would write ONE parameterized adapter (~150–250 lines, ESTIMATE) with per-seat config, not four near-identical bodies of code. The per-seat duplication means every protocol fix lands four times or rots in three places. The 15-check arm test should be halved: any check that has never failed is a prayer, not a test; keep only checks that have caught a real fault.
- **The concrete waste:** the ceremony-to-output ratio is the tell. Two-thirds of a month's allowance bought 586 lines. The tooling measures *spend* exquisitely and *output* not at all. There is no per-agent cost-per-accepted-line metric, which is the only number that would have caught the Aug 21–22 disaster within hours instead of days. Build that one metric; delete a layer of something else to pay for it.
- **Deeper cut, adversarially:** ask whether 5 seats is engineering or collecting. Each additional seat adds integration surface, and the marginal seat's value is unmeasured. A competent engineer would demand a bake-off: same task set through each seat, keep the top two or three, drop the rest. (ESTIMATE of seat-count value; no benchmark exists in the record to cite.)

**Where my adversarial argument is strongest (the case against the status quo):**
1. **The subsidy is the architecture.** The operator's own words confess it: "if it wasn't for a grokbot sub what are we even doing?" A rig designed around extracting a 13–14x subsidy is long the vendor's marketing budget. Marketing budgets get cut in one planning cycle. This is not infrastructure; it is a coupon.
2. **ToS fragility (the underpriced risk).** Consumer subscriptions routinely prohibit or restrict automated, orchestrated, non-interactive use of seats. Wrapping four consumer seats in MCP stdio servers driven by an orchestrator is precisely the pattern those terms target. One enforcement action kills all four seats simultaneously — correlated, instant, no SLA, no appeal queue a one-person shop can afford to wait in. (Flagged as risk assessment, not a cited ToS quote — operator should read the current terms of each vendor.)
3. **The caps bind at the worst time.** Rate/usage limits throttle exactly during the high-output weeks the shop is built for. The incident proved it in reverse: the allowance, not money, is the real budget.
4. **No independent meter.** All usage truth is vendor-reported. In a pay-per-token world, the bill IS the audit.

**Where my own argument is weakest (honestly):**
- The math. At this volume the alternatives cost 2–5x more for the same or lower quality, and a single non-coder operator cannot realistically run GPU infrastructure — the ops burden would consume the orchestration time that is the shop's actual product. Arguing for honesty of billing over a 13x subsidy is arguing the shop should pay ~$600+/mo extra (ESTIMATE) for ideological cleanliness. That is a hard sell while the coupon prints.

**RECOMMENDATION:** Keep the subscriptions — but as a bridge, not a foundation. Concretely: (1) build the thin API lane NOW as a metered fifth seat (the allowance-check tooling already exists — this is what it was actually for), routed through a router, handling maybe 5–10% of traffic, so the shop learns its true per-token cost curve from real data instead of my estimates; (2) never again let a single vendor exceed ~40% of delivered model value; (3) let the xAI annual seat expire Dec 1 without renewal unless a bake-off justifies it (sunk-cost seat); (4) skip owned/rented GPU entirely at this volume. **Switching cost if the subsidy ends:** low, IF the API lane is already warm — the MCP adapter pattern is billing-agnostic by design, so swapping a subscription seat for a keyed seat is a config change. If the lane is cold when the week comes, switching cost is 1–2 weeks of degraded throughput while keys, budgets, and per-seat cost models get built under pressure. The plan for the week the subsidy ends is to have already left, partially, on your own schedule.

BIGGEST RISK NOBODY NAMED: **The rig optimizes the vendor's metric, not the shop's.** Every guard measures spend against an allowance the vendor defines and reports. Nothing measures cost per accepted line of shipped product. So the shop can be perfectly "efficient" — 13x subsidy captured! — while producing 586 lines a month. The subscription model doesn't just risk repricing; it actively hides the only number that matters, and the incident proved it: the failure was detected by the needle, not by the output. A business that meters its inputs and not its outputs will optimize its way into buying very cheap nothing.
